# 我在 Mac 上用 Claude Code 踩过的坑

我用 Claude 写中文口播、改脚本，也让它在项目里改代码。最影响干活的两次经历，一次是手机已经扣了钱，打开 Claude 还是免费版。另一次是项目做到一半要换账号，手头的对话也跟着断了。这两个问题最后用了完全不同的办法解决。

## 套餐怎么选，我先看自己卡在哪里

我现在手头有三个 Pro。让我开始研究多个账号的，是手上的活做到一半碰到用量上限，再开个窗口又得重新交代背景。按量加购的成本我接受不了，所以我先把力气花在了怎么续聊上。

我见过有人用 Pro 好几个月，刚升 Max 账号就受限。这件事让我升级前多想了一步，但我看不到平台的处理原因，也没有足够的样本给 Pro、Max、Ultra 排一个“封号概率”。如果一个 Pro 已经够用，这个仓库从一个账号就能用起来。

## 钱扣了，Claude 怎么还是免费版？

我用 Apple 礼品卡余额新订阅时，遇到过扣款成功、Claude 里却没出现 Pro。最耽误时间的是，我的 iCloud 和 App Store 用了不同的 Apple 账户，一开始连该去哪个账号找订单都没弄清楚。

现在我会先对两件事。第一，打开 Apple 的收据，看**哪个 Apple 账户付了这笔钱**。第二，打开 Claude，看**当前登录的是哪个邮箱、显示什么套餐**。仍显示免费，就用购买时的商店账号尝试恢复购买。已经扣款又恢复不了，拿着原订单联系支持或申请退款，先别重复下单。我的经历也推不出“第一次退款一定过”的规律。[Apple 恢复购买](https://support.apple.com/zh-cn/108096) · [Apple 退款入口说明](https://support.apple.com/zh-cn/118223) · [Claude 订阅账单说明](https://support.claude.com/en/articles/8325618-paid-plan-billing-faqs)

后来我也试了 Android。在 Claude 应用里选升级，走 Google Play 的付款流程，这一次 Pro 顺利到账。我记下的是这次实际用的商店账号、Claude 邮箱和开通结果。换一笔订单，仍要把这三项对一遍。[Claude 的 Android 订阅说明](https://support.claude.com/en/articles/9612892-how-do-i-sign-up-for-claude-pro-on-claude-for-android)

## 邮箱能登录、付款成功、身份验证通过，是三件事

我遇到过新邮箱已经能登录，过一会儿又被要求验证手机号。也遇到过 Claude 刚升级就弹出身份验证（KYC），那次我按官方页面提示用自己的证件完成了验证。前者要去邮箱服务商处理，后者要走 Claude 给出的验证入口。先看清是哪家在提问，就少走一趟弯路。

至于“刚注册弹验证”和“用了很久才弹验证”分别意味着什么，我只知道自己看到了提示，没有平台给出的具体判定原因。出现时间不足以预测验证结果。[Claude 身份验证说明](https://support.claude.com/en/articles/14328960-identity-verification-on-claude)

## 从桌面和 CLI 各登一个号，到同一个窗格里续聊

两个号的时候，我在桌面端登一个，CLI 登另一个，用起来很直观。直到菜单栏和终端底栏都显示了桌面账号的额度，我才发现，光看一个百分比根本不知道它算的是谁。现在我先在对应的 CLI 配置里用 `claude auth status` 核对身份，再用 `/usage` 看这个账号的五小时和周额度。一个窗口剩 100%，另一个只剩一点，完全可能同时为真。

加到三个账号后，我看过 CC Switch 和 Magpie。我的项目本来就在 cmux 里，我最想保住的是眼前这个窗格，以及刚讨论过的代码和决定，所以做了个本地接力实验。

1. **登录交给 Claude。** A 用默认配置，B 和 C 分别用独立的 `CLAUDE_CONFIG_DIR`。每个配置第一次登录时，由官方 Claude Code 打开浏览器，我在 Claude 的页面选账号并授权。三个配置分别用 `auth status` 核对。我就遇到过给 C 授权时浏览器又选中了 B，目录名写对了也得看实际邮箱。[官方多账号登录说明](https://code.claude.com/docs/en/authentication#log-in-with-multiple-accounts)
2. **什么时候换，由我的脚本决定。** 当前一轮做完，脚本才读 `/usage`。五小时或周额度任一项剩 **5% 或更少**，并且没有后台任务、没有正在输入的草稿时，才找下一个有余量的账号。留这 5% 是因为我吃过任务中断的亏。一轮特别长的任务还是可能先用完额度。登录失效、账号受限或用量读不清，脚本会暂停。
3. **接过去的是已经保存的对话。** 脚本在同一个 cmux 窗格里，用下一个账号重新启动官方 Claude Code，把刚保存的记录交给 `--resume`，再用 `--fork-session` 从这里开一个分支。原项目文件还在原目录，下一句可以沿着刚才的讨论接着问。正在执行的命令无法靠聊天记录恢复，已有的对话内容则会带进下一个账号。[Claude Code 续聊参数](https://code.claude.com/docs/en/cli-reference)

仓库现在也提供了从这套本机实验整理出来的 5% 接力脚本，可以先用自己的两个 Pro 在一个窗格试，再决定是否接到 cmux 快捷键。官方文档介绍了多个账号分别登录的方法，对按额度自动轮换，我没有找到官方许可或账号安全保证。[仓库里的账号用法](accounts.md)

## 网络和设备，我尽量一次只变一件事

我之前在 Windows 上接连遇到过账号受限，一度怀疑设备被标记。后来换了 Mac，也同时调整了出口和分流，几个条件一起变了，我没法把原因单独归到 Windows 或那台机器。真正留下来的经验是，先用一套自己熟悉、方便查记录的环境。下一次出问题，至少知道刚动过哪里。

我自己用过机房出口。选网络时，我更在意日常使用能否保持稳定，以及能不能看清一条请求到底走了哪里。我的检查顺序是：

- **先看 Claude 的真实请求。** 在 cmux 里发一句话，到代理连接记录里按时间找对应域名，看命中了哪条规则、最后走哪个节点。浏览器打开 IP 查询页，只能说明那次网页访问的出口。
- **再看是谁解析了域名。** 开了 fake-ip 后，Mac 上可能只看到代理分配的本地地址。要确认上游 DNS，得另外核对解析器和查询记录。
- **浏览器单独查 WebRTC。** 我会在实际使用的浏览器里看它通过 WebRTC 暴露了什么地址。这个结果和终端里那次 Claude 请求各记各的。[网络检查与分流示例](network.md)

我的日常任务本来就是中文写稿、剪视频和改代码，我照常用中文提问，也没有为了账号去改系统时区或作息。手头只有一条稿子，就让它把这一条做完。对我的工作来说，能核对付款、查明请求走向、捡回上一次对话，比猜一套平台风控规律更有用。
